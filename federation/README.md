# Федеративный обмен ДАО КООПЕХ

Протокол, по которому узлы сети обмениваются фактами: предложениями каталога, сделками, обязательствами, отзывами, якорями документов.

Узел — это организация. Она либо стоит на нашем региональном хабе, либо держит свой бэк-офис: Odoo (сборка Rudoo), 1С ERP, 1С-Битрикс, Битрикс24, WordPress, Cyclos. Для сети разницы нет: узел обязан уметь ровно пять точек HTTPS и подписывать свои события.

## Что здесь лежит

| Путь | Что это |
|---|---|
| `spec/event.schema.json` | Конверт события: поля, ограничения, правила подписи. |
| `spec/events.md` | Типы событий версии 1 и кто вправе их публиковать. |
| `spec/openapi.yaml` | HTTP-контракт узла. Пять точек, из них обязательны две. |
| `ref/` | Справочная реализация на чистом Python: канонизация, Ed25519, журнал, вывод состояния сделки. |
| `ref/test_federation.py` | 31 тест, включая векторы RFC 8032. Зависимостей нет. |

Проверить, что всё сходится:

```bash
python federation/ref/test_federation.py
```

## Четыре правила, на которых держится всё остальное

**1. У каждого факта ровно один авторитетный узел — тот, о ком факт.** Кооператив «Борозда» публикует свои предложения, свои акты, свои обязательства. Событие о чужом объекте отбрасывается на входе. Это правило снимает почти все конфликты слияния: их просто нет, потому что писать в одну запись с двух сторон некому.

**2. Двусторонние объекты требуют двух подписей.** Состояние сделки нигде не хранится — оно вычисляется из событий обеих сторон (`ref/deal.py`). Пока акт подписан одной стороной, сделка ждёт вторую, и никакие действия первой этого не меняют. Отсюда следует, что общий консенсус сети не нужен: договариваются двое, и двух подписей достаточно.

**3. Внутри узла — ACID, между узлами — согласованность в конечном счёте.** Деньги, остатки, проводки живут в PostgreSQL одного узла и подчиняются транзакциям. Через границу узла проходят не изменения состояния, а подписанные заявления о фактах.

**4. Порядок есть только внутри журнала.** `seq` и `prev` дают полный порядок и неизменяемость журнала одного узла. Между журналами порядка нет и не нужно — события приходят вперемешку и с задержкой, результат от этого не меняется (проверяется тестом `test_order_of_arrival_does_not_matter`).

## Почему не блокчейн и не OrbitDB

Распределённая база с разрешением конфликтов решает задачу, которой у нас нет: договориться о едином состоянии между незнакомцами без доверия. У нас другое — двусторонние отношения известных сторон, каждая из которых отвечает за свои факты. Двух подписей хватает; глобальный консенсус означал бы, что посторонние узлы участвуют в наших сделках.

Разбор стека целиком — в `docs/architecture-federation.md`.

## Куда это переедет

Спецификация и справочная реализация временно живут в репозитории прототипа, потому что своего репозитория у сети ещё нет. При переносе на Odoo уезжают в `dao-cooptech-federation` — отдельно и от прототипа, и от `dao-cooptech-odoo`: по этому контракту будут писать интеграторы 1С и Битрикса, которым остальные два репозитория не нужны.
