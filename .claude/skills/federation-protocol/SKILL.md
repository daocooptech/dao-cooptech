# Федеративный обмен: как устроен и как его менять

Спецификация и работающий эталон лежат в `federation/`. Эталон не рабочий узел — ни сети, ни хранилища; это исполняемый образец формата, по которому сверяются реализации на других стеках.

Проверить, что всё сходится:

```bash
python federation/ref/test_federation.py
```

50 тестов, зависимостей нет, включая векторы RFC 8032 для подписи.

## Семь правил

1. **У каждого факта ровно один авторитетный узел — тот, о ком факт.** Событие о чужом объекте отбрасывается на входе.
2. **Исключение одно: двусторонние объекты.** Сделка и линия взаимного обязательства симметричны, авторитетного узла у них нет. Их состояние определяется наличием подписей обеих сторон.
3. **Внутри узла ACID, между узлами — согласованность в конечном счёте.** Через границу проходят не изменения состояния, а подписанные заявления о фактах.
4. **Порядок есть только внутри журнала** (`seq` и `prev`). Между журналами порядка нет и не нужно.
5. **Подпись обязывается хэшем тела, а не телом.** Поэтому адресное событие отдаётся постороннему без содержимого, и цепочка не рвётся. Без этого выборочное раскрытие и проверяемость исключают друг друга.
6. **Ключ проверяется на момент события.** Плановая смена не отменяет старые подписи; компрометация помечает более поздние события сомнительными, но не стирает их.
7. **Алгоритм подписи лежит в конверте и под подписью.** Ed25519 обязателен; ГОСТ Р 34.10-2012 заложен опцией. Событие с неподдерживаемым алгоритмом отклоняется, а не принимается на веру.

## Как добавить тип события

1. Опиши в `federation/spec/events.md`: тип, кто вправе публиковать, состав тела. Имя — `предмет.действие` строчными, например `deal.act.signed`.
2. Если появились новые поля-значения, добавь их в `$defs` схемы `federation/spec/event.schema.json`.
3. Напиши тест в `federation/ref/test_federation.py` до кода, а не после.
4. Проверь, что чужой узел не может повлиять на состояние: тест вида «третий подписал — состояние не изменилось» обязателен для всего двустороннего.

## Что нельзя нарушать

**Дробные числа запрещены везде.** Деньги и количества — строкой с фиксированным числом знаков: `{"amount": "1234.56", "currency": "RUB"}`. `0.1 + 0.2` в разных языках даёт разные байты, значит разные подписи, значит журнал не сойдётся между Python, PHP и 1С.

**Каноническая сериализация одна на всех** (`federation/ref/canonical.py`): UTF-8, ключи по кодовым точкам, без пробелов, экранирование по RFC 8785. Свою не изобретать.

**Обязательных точек HTTP всего две** — `GET /.well-known/did.json` и `GET /federation/log`. Остальное ускорения. Порог входа меряется одним числом: сколько времени у стороннего разработчика уходит на первый работающий узел. Больше дня — упрощаем протокол, а не пишем документацию.

**Неизвестный тип события пропускается молча**, но сохраняется как есть — иначе сеть развалится на несовместимые поколения.

**Обработчик события детерминирован и идемпотентен.** Никаких `now()`, `random()`, последовательностей и обращений наружу: повтор обязан дать тот же результат, иначе узлы тихо разъедутся, и обнаружится это через полгода при сверке.

## Идентичность

Организации — `did:web` (документ с ключами на домене организации). Люди — `did:key`: ключ и есть идентичность, она не теряется при переезде между узлами. Наоборот делать нельзя — человек не владеет доменом кооператива.

Техническая подпись (Ed25519, целостность журнала) и юридическая (КЭП, ГОСТ Р 34.10-2012, для документов в ФНС) — два разных контура. Одна не заменяет другую.

## Персональные данные

Широковещательное событие не содержит персональных данных никогда. Личное идёт адресно, в поле `to`. Вложения с персональными данными и коммерческой тайной хранятся только шифрованными, ключ файла остаётся у узла-владельца, **удаление — это уничтожение ключа**: из контент-адресуемого хранилища данные не изымаются.
